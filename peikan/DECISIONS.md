## 2026-10-23 · 骰子被掷了两次，还拿错了后果

**症状**（真机）：10-23 只醒了一次，而当天还有 12–14、20–23 两个窗口没走。
`rhythm-state.json` 里 `plan.action = "skip"`，下一趟直接排到明天 07:00。

**根因两层，其实是同一件事**：

1. **骰子挪了位置又被掷了两遍**。`makePlan` 里掷一次 `skipChance`，醒来时
   `withBrain` 又掷一次。同一个 30% 算了两回，实际跳过率约 51%。
2. **skip 的代价标错了**。`planToTimestamp` 对 `skip` 返回 `null`，
   `scheduleNext` 就退到「明天第一个窗口」——于是「这个窗口不想看」被实现成
   「今天到此为止」。文档里写的明明是「窗口 = 一次机会」。

**修法**：

- `makePlan` **不再掷骰子**，只决定「几点醒」。看不看在醒来那一刻（`withBrain`）才掷，
  与注释里的原话对齐：*每次醒来独立掷*。
- `skip` 因此不再出现在计划里；醒来不看只花掉这一个窗口，`markWoke` 之后照常
  在当天剩下的窗口里排下一趟。
- `rhythm.wake` 入口加一道额度兜底：排程可能带着过期任务醒来，到点了也不该再跑。

**验收**：`verify/skip-day-check.mjs`（5 例）。已反向验证：把 `rollSkip` 放回
`makePlan` → 转红；恢复即绿。

**教训**：同一个概率写在两处，两处都「没错」，合起来就是另一个数。
还有——一个状态值（`skip`）没有时间点时，它的排程语义是**默认值**决定的，
不是写文档的人决定的。

## 2026-10-23 · 有人找她的时候，不掷「今天不想看」

**问题**：`skipChance` 不分回合。他刚私信她，她也有三成概率整轮跳过——
**既没看视频，也没回话**。日志上只写「没看」，看不出「没理人」。

**判断**：看不看是她的事，回不回是别人的事。前者可以掷骰，后者不能。

**修法**：先定回合，再掷骰；`skipChance` 只对 content 回合生效。

**验收**：`verify/social-skip-check.mjs`（3 例）。已反向验证：去掉 `!isSocial` 条件 → 转红。

## 2026-10-23 · 手动叫醒与作息分开记账

**问题**：日志和界面上出现过「已醒 4/3」「5/3」「6/3」，一天甚至爬到 12/3。
数字本身不是 bug，是**两个问题被写进了同一个计数器**：

- 她今天**自己**醒了几次（作息有没有节制）
- 今天**被叫**了几次（人急不急）

上限 `maxWakesPerDay` 的语义是前者。以前两者共用一个 `wakes`，于是
「手动绕过配额 +1」一路把它顶出上界，界面上只剩一串看不懂的数字，
真正该看的那个数被淹掉了。

**修法**：

- `wakes` 只由生物钟写（`markWoke`），受 `maxWakesPerDay` 管。
- 新增 `manualWakes`（`markManualWake`），**不占作息额度**，只受
  `maxManualWakesPerDay`（默认 10）这个防抖上限管——一次误触不该让她连跑十轮。
- 手动叫醒**不重算计划**：她的作息不该因为被叫了一声就改钟。
- `bili_my_day` / 侧边栏 / 总览页都把两个数分开报。

**顺带修的**：`markWoke` 之后调用方又多调了一次 `planAndSave`，
`history` 里一直是成对的重复条目（相隔 1 毫秒），一并去掉。

**验收**：`verify/wake-accounting-check.mjs`（5 例）+ `skip-day-check` 里的 history 用例。

## 2026-10-23 · 他发来的视频，排一队等着被看

**问题**：他私信里丢两条视频链接，她回了话，**那条视频她一次都没打开**。
原因不是懒：social 回合的工具表里只有 `bili_inbox` / `bili_reply`，
content 回合只看推荐流——两条路没有交集，「他发给你看」在代码里根本不存在。

**修法**（不破坏 P0 的回合解耦）：

- 新增 `lib/linkqueue.js`：从主人发来的私信/评论里抠出 BV，落 `watch-queue.json`。
  同一 BV 只排一次；**真 debrief 成功**才划掉（回过话不算看过）；30 天没看自动过期。
- content 回合的 prompt 里列出「他发给你的、你还没看的」。
- social 回合**只多一只读的手**：`bili_debrief`，而且只在队列非空时才给；
  运行时再一道门——只能读**队列里那一条**，想顺手刷别的，门关上。
  赞 / 评论 / 递 / 关注 一个都不给：看是只读动作，不是对外发言。
- `b23.tv` 短链会尝试展开（manifest 加了这个域）；展不开就老实标成「没展开，你可以问他」，
  不假装看过。

**验收**：`verify/linkqueue-check.mjs`（17 例）+ `verify/forward-watch-check.mjs`（8 例）。
已反向验证：去掉「只能读队列里那条」的门 → forward-watch 转红。

**复查拓出来的（我自己第一版写错的）**：入队只按私信那条路的字段取正文（`body || text`），
而 `msgfeed.poll()` 的条目根本没有 body/text，正文在 `source` / `title` 上。
于是**私信里的链接能进队，评论 / @ 里的永远进不去**——而这条决策写的是「私信/评论」。
现在抹平在 `linkqueue.textOfMessage` 一处，入队循环收成 `collectFromMessages`（可测），
集成测试直接喂真实字段形状的两种条目。反向验证：把 `source || title` 去掉 → 转红。

**教训**：两个来源的字段名不一样，而我在两处各写了一遍取正文。
「同一个行为多个出口」这次没犯，倒在了「同一个概念两个形状」。

**没做的**：没有把转发变成「立刻停下手上事去看」。她有自己的节奏——
排进队里，下一轮看。真急着要她看，手动叫醒她（那时队列就摆在 prompt 第一屏）。

## 2026-10-22 · 推理吃空预算自动翻倍重试（P2-1）

**问题**：真跑验证中 `group/auto-hy3` 一次思考就把预算（默认 8000）吃空——
正文 0、工具 0 → `think` 直接 `ok:false` → 整轮废掉，只能等规则兜底。
日志表现为「brain 无产出 → 规则兜底」，一天里反复发生。

**修法**：`think` 检测到「推理吃空预算」时，若预算未达硬顶（32000）且未重试过，
**翻倍预算重试一次**（同一 round），给推理模型「多思考出正文」的机会。仍失败才返回。
硬顶从 16000 提到 32000。

**设计取舍**：只重试一次（`retriedOnce` 锁死），防止推理模型无限烧预算死循环。
这只影响「推理吃空」这一个失败路径，不改变正常流。

**验收**：`verify/reason-budget-retry-check.mjs`（3 例：吃空→翻倍重试成功 / 两次吃空→失败且只调 2 次 / 正常只调 1 次）。
已反向验证：注入「不重试」旧逻辑 → 测试转红，恢复即绿。

## 2026-10-22 · 分享上限「cfg.quota 缺失回落 3」修复（真跑验证暴露）

**症状**：方案 3 完整真跑时，日志出现「今日已推 3 条（上限 3）」，
但配置 `shareDaily=5`、`bili_quota` 工具也显示 cap 5。

**根因**：`shareNote` 只从 `cfg.quota.shareDaily` 取上限。
若某条调用链里 `cfg.quota` 缺失，`{...quota.DEFAULTS, ...cfg.quota}` 只剩
DEFAULTS 的 3，静默把分享上限变成 3。于是「自动分享用 3、quota 工具显示 5」两套账。

**修法**：上限优先序改为 `opts.maxPerDay > cfg.quota.shareDaily > cfg 顶层 shareDaily > DEFAULTS`。
`cfg.quota` 缺失时回退读 `cfg.back shareDaily`（`readConfig` 保证给），仍缺才用 DEFAULTS。

**教训**：真跑验证（不是 verify 静态测试）才抓到——verify 全绿时这个 bug 藏得好好的。
它和「同一个行为多个出口」是同一类病：接口的数字没统一到一处读。

**验收**：`verify/share-cap-fallback-check.mjs`（4 例，钉死回退链）。
已反向验证：注入旧逻辑（无顶层回退）→ 测试转红，恢复即绿。

## 2026-10-22 · 回复与分享分轮（P0）

**问题**：他私信/评论里回了她，她回完话，**同一个回合里又推了一条视频**。
于是「回一条私信」总是捎带「推一条视频」——回复和分享挤在同一轮。

**改法**：**一个回合只做一类对外动作**，靠工具表隔离，不靠 prompt。

| 回合 | 触发 | 工具表 |
|---|---|---|
| social | 有人找她（inbox.tick） | 只有 `bili_inbox` / `bili_reply` |
| content | 生物钟到点 / 手动 | 其余（看 / 递 / 评论），**剔除 `bili_reply`** |

**为什么用工具表而不是 prompt**：prompt 里写「别一起做」是把责任推给模型的自觉，
跟「先看收件箱」那次栽的是同一个跟头。工具表里没有那只手，她想捆都捆不了。
（三重兜底：工具表过滤 + `makeToolRunner` 里对写手做回合校验 + `wakeOnce` 自动分享门排除 social。）

**顺带修的**：

- **分享上限统一到 quota 一处**。此前四套数字并存
  （`config.shareDaily` / `config.shareMaxPerDay` / `quota.DEFAULTS.shareDaily` / 代码默认），
  日志里出现过「今日已推 3 条（上限 2）」。现在 `shareMaxPerDay` 仅作旧配置兼容，不再被消费。
- **同一轮不再重复拉收件箱**（P0-2）。social 回合由 inbox.tick 拉过并把 `pendingCount` 传进来复用。
- **note id 加随机后缀**，防同毫秒写两条撞 id。

**新增验收**：`verify/round-decouple-check.mjs`（13 例）、`verify/share-limit-check.mjs`（4 例）。
已做反向验证：注入「自动分享不再排除 social」的 bug 后 round-decouple 转红，恢复即绿。

## 2026-10-20 · 三个「节制」缺口补齐

对照源仓库 `dsh-bili-whale` 的 24 个命令，查出三处它写死、我没做的限制。

### ① 风控熔断（新 `lib/risk.js`）

**源仓库的原话**：
> 12015: 需要评论验证码（说明被风控盯上了，停手）
> 否则 agent 会把「被风控拒了」当成「发成功了」，绕过了「撞风控立刻停手」的红线

**我的问题**：只判 `code === 0`。被限流当成普通失败，下一轮接着撞。撞多了号会废。

**决定**：三种状态

| 级 | 触发 | 行为 |
|---|---|---|
| cooldown | 412 / -352 / -412 | 冷却数小时，期间所有写通道拒绝 |
| manual | 12015 / 12016 / -101 | 冷却 24h，**过期也不自愈**，要人处理 |
| ignore | 65004 / 65006 / -404 / -400 | 不拉闸（正常业务结果） |

**接入点**：publish / dynamic / social / likes / retract 五个通道，各自 `check` 进闸 + `record` 撞闸。

**为什么分 manual**：验证码只能人去点。自动恢复等于假装没事，下一轮继续撞。

### ② 同一视频 7 天冷却

**源仓库**：`同一视频 7 天内一次`

**我的问题**：`share-state.json` 整个按天重置，跨天就忘了。只有「今天推过」这一层。

**决定**：状态里加 `recent: [{bv, at}]`，**跨天保留**，90 天滚动裁剪。默认 `sameVideoDays: 7`。

**为什么不是永久**：永久不重复会让好视频永远推不出去（她可能三天后才发现它值得推）。7 天是源仓库验证过的窗口。

### ③ 同一人 30 天只回一次

**源仓库**：`同一个人（可选）30 天只回一次`

**我的问题**：完全没有。同一个人追着聊，一天能回十次。

**决定**：`canReply` 加第 ④b 道。默认 `sameSomeoneDays: 30`。

**主人豁免**：`ownerMid` 不受这条限制——但主人由 kill switch 和配额管，不是没人管。

**为什么这条重要**：这是「人际上的分寸」，不是技术限制。追着一个人说话会让人不适。

## 2026-10-20 · 有未回消息就不分享

**问题**：主人在私信里回了她，她直接去看视频并分享了，一句没回。

**原来的做法**：prompt 里写「建议流程（不必严格照做，你有判断权）：1) 先调 bili_inbox…」
**三重退路**——建议、不必照做、你有判断权。她当然跳过。

**决定**：代码门。查未回私信 + 未回评论，`pendingCount > 0` 就不分享。

**为什么写进代码而不是 prompt**：prompt 里的「建议」等于把责任推给模型的自由发挥。
自由是给她「看什么」的，不是给她「先不看人」的。
