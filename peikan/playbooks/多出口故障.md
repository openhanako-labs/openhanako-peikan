# 一个行为，多个出口

> 类型：故障卡
> 触发：改动某个「行为」时
> 首次：2026-10-20 · 一天内犯三次

---

## 症状

写了一个功能，测通了，交付了。用户一用就发现「另一个地方没生效」。

**报错原文（同一天内出现的三种形态）：**

```
任务 A：ask 的错误详情加了，think 的没加
      → think 报错仍然只有一个笼统的 PROVIDER_ERROR

任务 B：笔记列表两个渲染分支，只改了「有标题」那个
      → 旧数据那部分仍然显示空白

任务 C：bili_note 工具加了元数据补全
      → 规则路径直接调 store.addNote，完全不经过那个工具
      → UI 上「有的有封面有的没有」
```

---

## 已知根因

**「这个行为」在代码里不是一个点，是一组出口。**

写完时只验证了自己走的那条路。其他出口因为不经过它，看起来「没坏」——但也没被修好。

**最容易漏的三类：**

| 类型 | 例子 | 为什么漏 |
|---|---|---|
| **同一能力两个函数** | `ask` / `think` | 名字不同，看起来是两件事 |
| **同一渲染两个分支** | 新数据 / 旧数据 | 只测了新数据（手里就是新的） |
| **同一行为两条路径** | 工具调用 / 直接函数调用 | 后者不经过前者的所有装饰 |

---

## 步骤与判据

### 改之前

1. **搜一遍这个行为的名字**
   ```
   grep -rn "addNote\|publishComment\|sendDm" lib/
   ```
   数出所有调用点。

2. **问：这些调用点是不是同一个语义？**
   - 是 → 必须一起改
   - 否 → 分别命名，别共用

### 改之后

3. **每个调用点都补一条测试**
   测试不测「函数能跑」，测「**每个出口都走了新逻辑**」。

4. **写一条「数出口」的测试**
   ```js
   // verify/note-outlets-check.mjs 的做法
   function findOutlets() {
     // 扫 lib/ 所有文件，找出调用 store.addNote 的
   }
   assert.ok(outlets.length >= 3, "出口数量变了，记得补测试");
   ```
   **出口数量变化时测试会报——这就是探测器。**

---

## 易错点

**① 把补全放在上层，而不是唯一出口**

```
❌ bili_note 工具里补全      规则路径绕过
✅ store.addNote 里补全      谁都绕不过
```

**补全逻辑要放在最底层那个「谁都绕不过」的地方。**

**② 修完之后忘了传参**

```js
// 判定逻辑加进 shareNote 了
shareNote(sdk, dataDir, note, { maxPerDay, toMid })   // ← cfg 没传
// 结果：沉默衰减那两行代码一次都没执行
```

**加了一个依赖配置的检查，要检查所有调用点都传了 cfg。**
这是「多出口」的子形态：**出口改了，入口没喂。**

**③ 注释里写了，代码里没写**

```js
// ✓ 有闸门
if (pendingCount > 0) { ... }
```
但这条只加在 `wakeOnce` 一处，`bili_share` 工具那条路没有。

**「有闸门」不是事实，是某个出口有闸门。**

## 探测器清单

项目里现有的「数出口」测试：

| 文件 | 查什么 |
|---|---|
| `verify/note-outlets-check.mjs` | 写笔记的所有出口都有元数据 |
| `verify/gate-coverage-check.mjs` | 每条写通道都过了闸门 |
| `verify/ui-coverage-check.mjs` | 每个能力都有界面入口 |

**新增能力时，先看这三个文件有没有覆盖；没覆盖就加一条。**
